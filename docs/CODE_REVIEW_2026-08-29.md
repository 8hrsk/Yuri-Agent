**Дата:** 2026-08-29 · **Ревизия:** `f29c783` (main) · **Версия продукта:** 0.7.0 (stage 8)

**Метод:** оркестрированный multi-agent review. Шесть независимых read-only агентов (четыре Fable 5 на backend, два Opus 5 на frontend) разобрали непересекающиеся зоны кодовой базы; оркестратор провёл объективные прогоны (build/vet/test/race/coverage/bench/audit), перекрёстную сверку отчётов и выборочную ручную верификацию всех утверждений уровня HIGH и CRITICAL.

## 1. Вердикт

Yuri — это **необычно дисциплинированный проект**. Архитектурные инварианты не просто задекларированы в `docs/ARCHITECTURE.md`, а реально продавлены в код: append-only журналы с проекциями, optimistic concurrency, SQL-триггеры, дублирующие доменные инварианты, deny-by-default policy перед каждым side effect, строгий JSON-контракт reflection с max-delta/range/cooldown guard'ами, последовательная редакция секретов, отсутствие XSS-поверхности во фронтенде. Тестовая дисциплина выше среднего: 26 пакетов зелёные, полный прогон под `-race` чист, покрытие Go — медиана ~65%.

При этом **зрелость слоёв неравномерна**. Дизайн и корректность в статике сильные; проблемы концентрируются в динамике под нагрузкой и на границах между слоями:

| Ось | Состояние |
|---|---|
| Архитектура и границы доверия | Сильно. Инварианты формализованы и проверяются кодом |
| Корректность в статике | Сильно. `vet` чист, race чист, тесты зелёные |
| **Горячий путь стриминга (Go→Wails→React)** | **Слабо. Главный источник деградации UX** |
| **Масштабирование по объёму данных** | **Слабо. Почти всё линейно растёт без обрезки** |
| Поведение при отказах и отменах | Средне. Несколько путей оставляют систему в подвешенном состоянии |
| Безопасность | Средне-сильно. Модель продумана, но два звена — заглушки |
| Frontend-производительность | Слабо. Мемоизации нет вообще, виртуализации нет |

Практический итог: **приложение корректно работает на свежей установке и деградирует по мере накопления данных**. Ни одна из найденных проблем не является дырой в безопасности с внешним вектором, но три HIGH-бага делают заявленные фичи (расписания, делегация на Codex, JSON-fallback провайдера) нерабочими в конкретных, воспроизводимых конфигурациях.

**Найдено 103 уникальные проблемы:** 1 CRITICAL, 18 HIGH, 48 MEDIUM, 36 LOW (плюс одна перекрёстная ссылка M-49 на уже учтённую находку).

## 3. Суть проекта: что это такое внутри

Yuri — локальный desktop-агент для **одного владельца**, без server mode и без multi-tenant. Собран как Wails-приложение: React-renderer + Go-ядро в одном процессе, но `Bridge` рассматривается как настоящая граница доверия — UI не может сам выполнить инструмент, прочитать keychain или изменить policy.

**Модель данных.** SQLite — единственный authoritative store; Pebble, FTS5-индексы и векторы объявлены производными и восстановимыми. Ключевой паттерн — **append-only журналы + перестраиваемые проекции**: `memory_versions`/`memory_heads`, `persona_versions`/`persona_heads`, аналогично для relationship и affect. Каждая мутация версионируется, снабжается evidence и обратима. Доменные инварианты продублированы SQL-триггерами (agent-scoping, alternating turns в peer-диалогах, depth=1 у делегаций, cooldown пар) — редкая и правильная практика: инвариант нельзя обойти, зайдя мимо репозитория.

**Слоистость контекста.** Каждый run получает неизменяемый `ContextSnapshot` со строго фиксированным порядком: `immutable_policy` → `identity_seed` → `mutable_persona` → `relationship_affect` → `core_memory` → `task_context` → `retrieved_history` → `current_conversation`. Ни один слой ниже policy не может выдавать разрешения. Внешние данные (tool output, файлы, сообщения плагинов) заворачиваются в JSON-конверты с provenance, а не конкатенируются как system instruction — это внятная, работающая защита от prompt injection.

**Провайдеры.** Два режима: `ModelBackend` (Yuri сама ведёт agent loop поверх OpenAI-совместимого Responses/Chat Completions) и `AgentHarnessBackend` (официальный Codex App Server через ChatGPT OAuth, где токены Yuri не видит). Antigravity намеренно отключён typed-ошибкой `unsupported_auth_mode` — проект принципиально не занимается piggyback'ом чужих OAuth-сессий. Это осознанная и, на мой взгляд, правильная позиция.

**Плагины.** Отдельный процесс, JSON Lines поверх stdio, версионированный конверт `yuri.plugin.v1`, лимит сообщения 1 МиБ, запуск в отдельной process group с SIGKILL по pgid, пустое окружение (секреты родителя не наследуются), повторная авторизация capability на каждый вызов. README честно оговаривает, что это ещё не OS sandbox.

**Автономия.** Reflection может менять личность только малыми bounded-дельтами с evidence и rollback-записью; scheduled runs получают только low-risk read tools; proactivity имеет quiet hours, daily ledger и per-type cooldown. Делегация — depth=1, пустой tool registry у сабагента. Границы автономии прочерчены аккуратно.

**Где живёт зрелость и где нет.** Слои `domain`, `context`, `reflection`, `security` выглядят завершёнными. Слои `desktop` (мост), `memory` (движок) и весь frontend несут следы быстрого наращивания функций: `chat.go` смешивает DTO-маппинг, оркестрацию, эмиттер стриминга и persistence; `client.ts` — резолвер бриджа, защитные декодеры и полноценный mock в одном файле; `global.css` — один файл на 8496 строк с 58 дублирующимися селекторами.

## 4. Пять сквозных проблем

Отдельные находки перечислены в разделе 5. Но большинство из них — проявления пяти системных паттернов. Чинить нужно паттерны, а не симптомы.

### 4.1. Горячий путь стриминга не оптимизирован ни на одном из трёх участков

Это **главная проблема проекта** и единственное место, где три независимых агента пришли к одному выводу с разных сторон.

Цепочка «токен модели → пиксель на экране» проходит три участка, и на каждом сделано худшее из возможного:

1. **Go-мост.** Каждая text-delta порождает отдельный `wailsruntime.EventsEmit` — JSON-сериализация + IPC на каждый токен, без батчинга ([chat.go:1159](../internal/desktop/chat.go)). Плюс `emitter.segments[i].Content += delta` — квадратичная конкатенация вместо `strings.Builder` ([chat.go:938](../internal/desktop/chat.go)). Плюс каждая дельта складывается в `emitter.events`, и весь этот массив возвращается вторым каналом в `ChatRunResult.Events` ([chat.go:535](../internal/desktop/chat.go)) — то есть **весь стрим передаётся через мост дважды**.
2. **Клиентский слой.** Из-за двойной доставки `runWithBridge` вынужден дедуплицировать события, считая `JSON.stringify(event)` как ключ Map ([client.ts:2574](../frontend/src/lib/client.ts)) — две сериализации на событие в горячем пути и Map, растущий до конца run'а.
3. **React.** `assistant.delta` создаёт новый объект conversation ([ChatView.tsx:484](../frontend/src/components/ChatView.tsx)) → меняется идентичность `selectedConversation` → инвалидируется `useMemo(timeline)` ([ChatView.tsx:351](../frontend/src/components/ChatView.tsx)), который заново прогоняет `flatMap(splitRunTraceForTimeline)` с полным клонированием **всех** трейсов диалога, потом две сортировки с `Date.parse` в компараторе. Результат раскладывается по компонентам, из которых **ни один не обёрнут в `React.memo`** (проверено: 0 вхождений во всём `components/`). Параллельно `scrollIntoView({behavior:'smooth'})` перезапускается на каждый токен ([ChatView.tsx:402](../frontend/src/components/ChatView.tsx)), а `new Intl.DateTimeFormat` конструируется для каждого сообщения на каждом рендере ([ChatView.tsx:67](../frontend/src/components/ChatView.tsx)).

При типичных 20–60 дельтах/сек и диалоге со 100 сообщениями и 50 трейсами это тысячи полных пересортировок, клонов и конструкций форматтеров в секунду. **Деградация линейна по длине истории**: свежий диалог ощущается нормально, полугодовой — нет.

**Порядок исправления (по соотношению эффект/риск):** батчить дельты в Go по таймеру 30–50 мс → убрать дельты из `ChatRunResult.Events` (это снимет и необходимость в дедупликации по `JSON.stringify`) → вынести буфер стриминга из общего `conversations` в отдельный лёгкий state → `React.memo` + стабильные колбэки → вынести `Intl` в модульные константы → троттлить автоскролл и уважать ручную прокрутку пользователя.

### 4.2. Ничто не обрезается: система линейно растёт по всем осям

Проект — local-first и рассчитан на годы работы, но почти каждая структура растёт неограниченно.

- **Аудит.** `audit_events` пишется на каждый tool call, notification, install, а также триггерами на каждую ревизию persona/relationship/affect. Ретенции нет. При **каждом старте приложения** `restoreProactivityLedger` вызывает `Audit.List(ctx)` **без лимита** ([proactivity.go:182](../internal/desktop/proactivity.go)) — проверено, это единственный вызов List без limit в кодовой базе — и раскладывает всю историю в вечные `map[ID]time.Time` и `dailyCounts`. Для идемпотентности хватило бы окна в 24–48 часов. Время старта и RAM растут вместе с возрастом установки.
- **Память.** `RecordRecall` («touch») проходит через полный `appendVersionTx`: копия content_text/content_json/summary в `memory_versions`, копия **всех** sources предыдущей версии, ещё одна полная копия контента в `memory_fts`, откуда старые версии никогда не удаляются. То есть **база и время FTS-поиска растут от количества чтений, а не записей** ([memory.go:765,1056](../internal/storage/sqlite/memory.go)).
- **Affect.** `affective_events` не чистится никогда, а `Decay` при каждом пересчёте читает весь журнал целиком ([affect.go:424](../internal/storage/sqlite/affect.go)).
- **Чат.** `ListConversations` возвращает **все** диалоги со всеми сообщениями, всеми run'ами и всеми tool call'ами ([chat.go:130](../internal/desktop/chat.go)); фронт кладёт это целиком в React state без обрезки и виртуализации, а при каждом переключении вкладки перезапрашивает заново (`ChatView` размонтируется).
- **Списки в SQLite.** `AuditRepository.List`, `ConversationRepository.List`, `ListByConversation` не имеют offset и допускают вызов без limit.

### 4.3. Системный N+1 в слое хранения

Почти все списочные методы репозиториев реализованы одинаково: `SELECT id ... ORDER BY ... LIMIT` — и затем **отдельный `QueryRowContext` на каждый id**. Затронуты `runs.go:209`, `tool_calls.go:150`, `audit.go:125`, `approvals.go:152`, `delegations.go:400`, `peer_dialogues.go:177`, `memory.go:428`, `persona.go:271`, `relationship.go:228`, `affect.go:229`.

Усугубляется двумя обстоятельствами:

- `SetMaxOpenConns(1)` ([open.go:41](../internal/storage/sqlite/open.go)) — осознанное решение «один writer», но оно означает, что **все** запросы сериализуются через одно соединение. `Audit.List` на 50k событий — это 50 001 round-trip, на время которых блокируются все писатели.
- Поверх этого мост добавляет свой слой N+1: `ListConversations` для каждой беседы грузит все сообщения, все run'ы и для каждого run'а все tool call'ы; `memoryView` для каждого источника каждой памяти делает отдельные `Conversations.Get` + `Messages.Get`.

Все нужные колонки уже выбираются в соседних `get()`-методах тех же файлов — исправление механическое: читать полные строки одним запросом и переиспользовать существующие сканеры.

Отдельно: WAL включён, но `synchronous` не задан, то есть действует FULL — fsync на каждый commit, включая «touch» при каждом recall и лизинги планировщика. Для локального desktop с бэкапами `NORMAL` — обоснованный компромисс. И: полный `PRAGMA integrity_check` выполняется при **каждом** старте существующей БД, а `onlineBackup` держит единственное соединение на весь цикл `backup.Step`, замораживая приложение.

### 4.4. Отмена и отказ оставляют систему в подвешенном состоянии

Пути «всё хорошо» проработаны, пути отмены — нет.

- **Отмена run'а не финализирует сообщение.** В Go `emit()` первым делом проверяет `contextErr(ctx)` и возвращает ошибку, не доходя до Sink ([runtime.go:569](../internal/agent/runtime.go)) — проверено. Значит при отмене `assistant.completed` не эмитится никогда, а обработчик `run.completed` во фронте не трогает статус частичного сообщения ([ChatView.tsx:518](../frontend/src/components/ChatView.tsx)). Результат: текст навсегда остаётся в `status: 'streaming'` — вечный typing-indicator, и кнопки «Повторить»/«Слушать» недоступны именно там, где нужнее всего.
- **Отмена хода убивает плагин целиком.** `Supervisor.InvokeTool` на `context.Canceled` вызывает `Stop`, то есть SIGKILL всей process group ([supervisor.go:351](../internal/plugins/supervisor.go)). Мягкий путь существует — `writeCancel`/`MethodCancel` — но **не вызывается нигде** (проверено grep'ом), а SDK-сервер его даже не обрабатывает.
- **Approval-каналы утекают.** Запись в `b.approvals` создаётся в `createApproval`, но удаляется только в `ResolveApproval`. Если пользователь не ответил (run упал, отменён, истёк) — запись живёт до перезапуска. Плюс заявленный 5-минутный `ExpiresAt` проверяется только в момент клика, а сам run ждёт до своего дедлайна (10 минут).
- **Ошибки approval и cancel проглатываются во фронте.** `handleApproval` и `handleCancel` — `async` с `try/finally` без `catch`, вызываются как `void ...` ([ChatView.tsx:585](../frontend/src/components/ChatView.tsx)). Отказ бриджа даёт unhandled rejection, диалог остаётся на экране без единого сообщения, Escape не работает, клик по фону не закрывает. Пользователь застревает на подтверждении опасной операции.
- **Уход с вкладки во время run'а теряет всё.** `ChatView` размонтируется при переключении вкладок ([App.tsx:128](../frontend/src/App.tsx)) — проверено. Run на бэкенде продолжается, но `runId`, `runStatus` и `pendingApproval` были локальным state. Худший случай: за время отсутствия пришёл `approval.required` — модалка не отрисуется никогда, run зависнет в ожидании решения, о котором пользователь не узнает.

### 4.5. Два звена модели безопасности реализованы как заглушки

Модель угроз внятная и в основном воплощена. Но два места держатся на честном слове, и это стоит зафиксировать явно, потому что README описывает их как работающие границы.

- **Проверка подписи плагинов не существует.** `packageTrust` умеет вернуть только `unsigned` или `unverified` — **оба с `devMode=true`** ([plugins.go:833](../internal/desktop/plugins.go)). Поле `SignatureVerified` выставляется в `true` ровно в одном месте — в тесте `runtime_test.go:175`. Значит guard `if !config.DevMode && !config.SignatureVerified` ([supervisor.go:97](../internal/plugins/supervisor.go)) недостижим в продакшене. Ed25519-подпись из манифеста валидируется только синтаксически, криптографически — никогда. Всё проверено вручную. В коде есть честный комментарий, что это заготовка под будущий trust store, и README оговаривает границу этапа — но **дополнительно** глобальный переключатель dev mode обходится любым вызовом `InstallPlugin{AllowUnsigned: true}` со стороны renderer'а ([plugins.go:170](../internal/desktop/plugins.go)), и вот это уже расходится с заявленной моделью.
- **Гранты плагинов — самоподтверждение.** `EnablePlugin` копирует **каждую** декларацию из манифеста в `PermissionGrant` 1:1, без срока действия и без выбора пользователя; пустой scope превращается в `ScopeUnrestricted`. Авторизатор затем сверяет грант с той же манифестной декларацией — что всегда истинно по построению. Runtime-медиация формально работает, но единственная реальная граница — решение «включить плагин целиком или нет». Плагин с `external.send` + `secrets.use` получает оба права одним кликом; выборочный отзыв невозможен.

Отдельно стоит отметить, что **сделано хорошо**: секреты последовательно не попадают в события renderer'а, audit и логи (предкомпилированные sanitize-регэкспы, `safeError`, контент filesystem-write заменяется хэшем); filesystem write реализован аккуратно (create через `os.Link`, replace с двойной проверкой SHA-256, `Lstat` против симлинков, атомарный rename); во фронтенде нет ни одного `dangerouslySetInnerHTML` и ни одного `console.*` — XSS-поверхности нет, а hidden reasoning модели жёстко не переносится в UI (`normalizeRunTraceStep` подменяет метки константами).

## 6. Что сделано хорошо

Отчёт по определению перекошен в сторону проблем, поэтому важно зафиксировать, что в этом проекте лучше, чем в типичном коде того же возраста и размера.

- **Инварианты продавлены в схему, а не только в код.** Доменные правила (agent-scoping, alternating turns, depth=1, cooldown пар) продублированы SQL-триггерами — их нельзя обойти, зайдя мимо репозитория. Это редкая практика и она окупается.
- **Append-only с проекциями применён последовательно** ко всем изменяемым сущностям: memory, persona, relationship, affect. Optimistic concurrency (`WHERE id=? AND version=?`) используется единообразно.
- **Миграции сделаны всерьёз:** embedded, с checksum-контролем, каждая в транзакции, с read-only `integrity_check` и owner-only (0600) online-снапшотом через SQLite backup API перед применением, с удалением снапшота при успехе и сохранением при ошибке.
- **Reflection guard — образцовый.** Строгий JSON-декодер (дубликаты ключей, unknown fields, trailing data), max-delta, range-проверки, cooldown, pinned traits, запрет неподтверждённого внешнего evidence — всё проверяется до применения, и один run на профиль одновременно.
- **Prompt injection закрыт структурно, а не фильтрами.** Внешние данные заворачиваются в JSON-конверты с provenance и попадают в слой ниже `immutable_policy`; порядок сборки контекста фиксирован и проверяется тестами.
- **Редакция секретов последовательна:** предкомпилированные sanitize-регэкспы, `safeError`, `slog`-редакция, fail-closed сообщения Codex, замена контента filesystem-write на хэш в audit. Ключ никогда не возвращается в `Config()` и не попадает в ошибки.
- **Filesystem write спроектирован аккуратно:** create через `os.Link` (no-replace), replace с двойной проверкой SHA-256, `Lstat` против симлинков, атомарный rename, точечный exact-path approval.
- **Backup-крипто корректно:** AES-256-GCM, свежая соль и nonce на каждый экспорт, scrypt с валидируемыми границами, заголовок как AAD, restore никогда не перезаписывает существующие файлы.
- **Plugin host решил неочевидные вещи правильно:** проблема «64 КБ `bufio.Scanner`» закрыта явным `scanner.Buffer(..., MaxMessageBytes+1)` с маппингом «token too long» → `ErrMessageTooLarge`; запуск в отдельной process group с SIGKILL по pgid; пустое окружение по умолчанию.
- **Frontend защищён от XSS структурно:** ни одного `dangerouslySetInnerHTML`, весь контент от модели, плагинов и файлов рендерится текстовыми нодами; ни одного `console.*` в `src/`; hidden reasoning жёстко не переносится в UI (`normalizeRunTraceStep` подменяет метки константами). В `src/` нет ни одного `any`.
- **`useVoice` — редкий пример аккуратного хука:** `mountedRef`, `cancelStartRef`, `discardOnStopRef`, интервал чистится в трёх местах, MediaStream-треки останавливаются.
- **Гонки запросов в `MemoryView` закрыты счётчиком `requestId`** — паттерн, который в большинстве проектов забывают.
- **Антигравити-решение.** Проект намеренно отказался от piggyback'а чужого OAuth/token cache и вернул typed `unsupported_auth_mode` вместо того, чтобы «как-нибудь заработало». Это дорогое и правильное инженерное решение.

## 7. Приоритизированный план

Порядок выбран по соотношению «эффект для пользователя / риск изменения», а не по severity как таковой.

### Волна 1 — сломанные фичи (дни)

Каждый пункт делает нерабочей заявленную функциональность в конкретной воспроизводимой конфигурации.

1. **H-1** — привязать расписания к `agentID`. Сейчас все расписания умирают после первого переключения агента.
2. **H-3** — переписать `newJSONStream` без SSE-фреймера + тест на `application/json`. Fallback не работает ровно в том случае, ради которого написан.
3. **H-2** — вывести вложенные run'ы из-под `modelTurns` gate. Делегация на Codex не работает вообще.
4. **H-8 + H-11 + H-10** — финализация сообщения при отмене, `catch` в approval/cancel, `max-height` и focus trap в диалоге подтверждения. Все три — блокирующие для пользователя состояния в approval-флоу, то есть в самом чувствительном месте продукта.
5. **H-5** — вынести `codexapp.Start` из-под `b.mu` и дать явный таймаут. Один зависший внешний процесс сейчас намертво вешает всё приложение.

### Волна 2 — производительность горячего пути (1–2 недели)

**Одна поправка к отчёту агента.** В M-2 исходная формулировка утверждала утечку `*sql.Rows` на двух error-путях. Проверка показала, что путь `rows.Err()` безопасен — `database/sql` закрывает Rows сам, когда `Next` вернул false. Реальная утечка возможна только на ошибке `Scan`. Находка остаётся валидной, но с более узким триггером.

**Чего этот review не покрывает:**

- **Профилирование не проводилось.** Все оценки производительности — аналитические, выведенные из кода (частота ре-рендеров, сложность операций, число round-trip'ов), а не измеренные. Порядок величин стоит подтвердить `pprof` на Go-стороне и React Profiler / Web Inspector Timeline на реальном длинном диалоге. Единственное исключение — `make bench-baseline`, который прогнан и воспроизведён.
- **Сетевые сценарии не запускались.** Выводы о поведении с реальными OpenAI-совместимыми шлюзами и Codex App Server получены статической трассировкой.
- **`EXPLAIN QUERY PLAN` на живой БД не выполнялся** — все утверждения об индексах основаны на сопоставлении SQL-запросов с `CREATE INDEX` в миграциях.
- **Криптоанализ бэкапа не проводился** — проверены режим, свежесть nonce/соли, KDF и AAD по коду.
- **Windows-путь не проверен** (`process_windows.go`), тестовые файлы просмотрены выборочно, контраст цветов оценён по значениям в CSS без инструментальной проверки WCAG.
- **Не покрыто чтением:** `internal/reflection/types.go` детально (993 строки), декодеры plugins/schedules/activity/peer-dialogues во фронте построчно против Go-структур, компоненты вне `ChatView`/`App` на предмет собственных перф-проблем.

**Что стоит сделать следующим шагом для валидации.** Три самые дорогие находки (C-1, H-6, H-16) проверяются дёшево и однозначно: снять React Profiler на диалоге со 100 сообщениями во время стриминга, посчитать `EventsEmit` за один ответ, и прогнать `EXPLAIN QUERY PLAN` на нескольких списочных запросах с наполненной БД. Это займёт час и либо подтвердит приоритизацию, либо перевернёт её.
