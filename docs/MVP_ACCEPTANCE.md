# MVP acceptance matrix

Статус этого документа отражает проверяемое состояние репозитория, а не только наличие отдельных компонентов. `Automated` означает, что критерий подтверждается локальным тестом без внешних credentials. `Partial` — основные части существуют, но отсутствует сквозная проверка или обязательный пользовательский шаг. `Missing` — обязательная часть критерия ещё не реализована.

## Текущий срез Stage 8

Текущие вертикальные срезы добавляют persistent `AgentProfile`, обязательное создание агента при чистом запуске, owner-defined identity/traits, roster selector, повторный flow создания дополнительных агентов, `agent.delegate`, bounded background peer dialogue, explicit read-only delegation scope, shared-memory publication, private peer episodes и directional social reflection. Profile/persona/relationship/affect создаются одной SQLite-транзакцией; conversations, runs, transcript archive/FTS и private memory адресуются `agent_id`, а переключение перемонтирует agent-scoped UI. Legacy rows транзакционно привязываются к мигрированному владельцу, background turn захватывает agent ID до запуска, а peer roster не раскрывает private preferences.

`agent.delegate` создаёт durable anonymous child run глубины 1 и связанную delegation-запись атомарно. Пустой scope сохраняет tool-less режим; явный scope выдаёт максимум три инструмента из `filesystem.read`, `web.search`, `web.fetch` только если они доступны parent run и проходят повторную execution-time policy. Субагент получает bounded task/context, отдельный immutable prompt, не более четырёх children на parent run и token/time/output limits, вычисленные из per-agent execution preset и известных model limits; balanced preset даёт максимум четыре model steps/три tool calls. Он наследует отмену, idempotency и redacted audit, но не получает persona, memory, transcript, roster, credentials, writable/external tools и не создаёт `AgentProfile`. Child tool trace виден live и после reload отдельным блоком «Субагент».

`agent.talk_to_peer` позволяет named root-agent поставить в фон начальное сообщение известному peer; владелец может запустить тот же durable exchange явной формой Collaboration. Ручная форма передаёт цель, opening message и необязательные верхние границы ходов, токенов и времени: backend пересекает их с preset инициатора и model limits, поэтому override может только сузить ресурсы. Отдельный read-only preview рекомендует лимит по структуре цели и aggregate-метрикам не более восьми завершённых диалогов выбранной пары, предпочитая похожие цели; он не вызывает provider, не создаёт run и показывает basis/sample count/confidence вместе с hard ceiling. Применение рекомендации остаётся явным owner action. При запуске backend повторно рассчитывает preview и отклоняет устаревшие или изменённые значения до создания run; эффективный budget сохраняется вместе с immutable origin и снимком рекомендации. Collaboration сравнивает этот снимок с фактическими ходами, токенами, временем и причиной остановки, а завершённые рекомендованные запуски агрегирует по исторической паре provider/model. Ручные и agent-default бюджеты в калибровочную выборку не входят. Ответы выполняются отдельными tool-less background runs. Для balanced preset новый exchange имеет диапазон 2–4 сгенерированных ходов, общий лимит 8000 токенов, 90 секунд, TTL, пятиминутный cooldown пары и один активный диалог на пару; efficient/extended используют более узкий/широкий bounded профиль, дополнительно сужаемый model limits. Каждый ответ возвращает `continue|complete`: semantic completion принимается только после минимума, legacy plain-text provider завершается после минимума как `implicit`, а max turns/tokens всегда останавливают цикл. Причина остановки и эффективный budget сохраняются и видны в Collaboration UI. Участники/provider фиксируются до goroutine, сообщения имеют run provenance, peer input остаётся untrusted data, а restart закрывает незавершённые записи без повторного provider call. Диалог не создаёт user chat conversation. После успешного завершения отдельные производные passes создают private episodic memory и bounded social reflection; persona, permissions и owner relationship при этом недоступны для изменения. Owner может просмотреть transcript, остановить активный run, увидеть только направленные мнения активного агента о peer и их evidence/version history. Сброс и откат создают новые append-only версии и фиксируются в audit как owner action.

Отдельный opt-in post-turn reviewer может автономно открыть такой же bounded dialogue, если выбранному peer действительно нужна независимая проверка. По умолчанию он выключен, не получает tools/private memory/system prompts, предпочитает `no_change` и формирует только sanitized purpose/message/reason. Quiet hours, отдельный daily limit/cooldown, один autonomous candidate на root run, восстановление ledger после restart и запрет второго dialogue после explicit tool-call проверяются автоматически. Collaboration UI показывает `agent_tool`/`autonomous` provenance и причину отдельно от transcript.

## Состояние Stage 7

Все 17 критериев имеют автоматизированное offline/CI-доказательство. Native WebKit flows закрывают onboarding и voice UI interaction; provider/Codex/plugin lifecycles, negative leak scan, prompt-injection agent loop, voice/chat contract, Codex logout UI и unsupported Antigravity contract проверяются специализированными smoke/contract tests.

Реальные OAuth credentials, платные provider calls, Developer ID, notarization и публикация артефактов не являются условиями локального OSS smoke-набора.

Для multi-agent memory проверяется отдельный isolation smoke: чужая `agent_private` запись не извлекается, явная `owner_shared`/`installation_shared` публикация становится доступна peer-агенту, а `revoke` исключает её из следующего retrieval без потери исходной версии и provenance.

Completed peer dialogue создаёт ровно по одной private episodic memory для двух участников с provenance на aggregate/turns. Она доступна релевантному recall, отсутствует в core snapshot и не видна третьему агенту. Повторный startup reconciliation не создаёт новую версию; interrupted post-completion projection восстанавливается. Failed/cancelled/expired exchanges episodic memory не создают.

Social-reflection smoke проверяет две независимые направленные модели `observer → peer`, evidence-linked opinion, небольшой affect event с decay и отсутствие изменений owner relationship/persona. Relationship/affect/idempotency marker коммитятся атомарно; повтор и recovery pass не вызывают модель второй раз после terminal marker. Secret-only transcript превращается в безопасный `no_change`, а wrong-subject/persona proposal не оставляет частичного состояния.

Peer-relationship curation smoke фиксирует observer один раз на Bridge-команду, не позволяет прочитать или откатить отношение через чужой `peerAgentId`, показывает opinion как субъективную оценку, а reset/rollback сохраняет предыдущие версии и owner audit trail.

Текущий набор запускается командой `make mvp-smoke`, а на macOS — `make macos-launch-smoke macos-ui-smoke macos-voice-smoke MACOS_APP=cmd/yuri/build/bin/yuri.app`. Первый включает race-enabled offline profile lifecycle, production-path plugin package lifecycle, Bridge → local OpenAI-compatible SSE lifecycle и Bridge → executable fake Codex app-server account lifecycle. macOS targets открывают собранный `.app` с изолированным profile root: lifecycle smoke проверяет `OnDomReady`/clean shutdown, onboarding smoke проходит welcome → agent profile → provider → success → Chat → создание второго агента → переключение на первого, voice smoke — recording → STT → agent → TTS → barge-in. Browser media/speech и provider response подменяются только на test-mode boundary; production backend paths проверяются отдельными race-enabled smoke.
